# 22 · 场景与物件占屏比例修正

日期：2026-10-24。版本：`20261024-R2`。接续用户“场景和道具比例明显有出入、道具太小”的反馈。这里的“道具”指物堆内可消物件；本轮不改三种功能按钮的美术。

## 1. 从截图量到什么

**【观察·近似框选】** 用户截图为 563×1000。容器可见外缘约为 x=5～562、y=235～790，横向占屏约 99%，下缘接近七格栏上沿。部分边缘被画面裁掉，椭圆／透视轮廓使矩形只能作为近似范围。

以几件较容易分辨的物件估算：胡萝卜圆片最长边约占屏宽 15%～19%，中间蒸饺约 16%，左下整个小蒸笼约 29%，左侧长油条约 38%。小蒸笼及其中包子不能按多个独立碰撞体计数。框选见本轮 `screenshot-measurements.json`，**是手工选取样本，不是整图实例分割或所有物件的平均尺寸**。

**【确认·项目实际画面】** R1 的农场图上物件小且集中在中央；容器下缘与栏位之间仍留有空隙。R1 的“大小区别”只恢复了不同类型间的相对倍率，没有修正过小的公共基础尺度，上一轮对此处理不足。

## 2. 源码和资源中确认的差异

### 2.1 竞品侧

**【确认·资源】** 本轮从冻结 402 data 再读出 7 个 Camera 对象。`LevelManager._mainLevelCameras` 指向 `sharedassets0.assets` 的 Camera pathID **534**，为正交相机，包内 `orthographic size=6.5`、全屏 viewport；其 Transform pathID 400 位于 `(0,0,-30)`，旋转为单位四元数。`MainSceneCamera` 的 size=3.4，双玩家相机 size≈4.7、各占半屏。这些是不同对象／模式的存储值，**不能声称 7 台相机同时渲染，或截图必然正在使用 size=6.5**。

**【确认·资源】** 同包 `LevelBoxPanel` Transform pathID 413 的局部 scale≈2.9；`Content` pathID 398 的 scale≈1.4，并绕 X 轴约 -90°；`ContentPointList` pathID 407 的 scale=1。这说明容器、内容父级和相机需要一起看，不能将不同工程中的一个 scale 数字直接相等。完整父链、坐标和原始数据 SHA-256 保存在 `competitor-camera-transforms.json`。

**【确认·静态】** 前轮恢复的 `LevelManager.GetObjSize` 常规路径返回 1，Season／GM 有另外分支，没有在该常规方法中看到按总库存数量缩小所有物件的计算。**这不是对所有生成方法和运行覆盖的排除证明**；不能据此断言竞品任何模式都不调整尺寸。

**【确认·资源】** 提取模型保留作者尺度，例如 `GTDinosaur` 预制体根 scale=1、模型子节点 scale≈1.406，烘焙后最长边约 1.863。项目将导入模型最长边统一为 1，再乘基础尺度；两边的单位、父级和相机视口均不同。参考模型相对倍率沿用 R1 的作者尺寸映射，不冒充其最终运行 scale。

### 2.2 项目侧

**【确认·项目代码】** R1 在 `Spawn` 中使用：

```text
base = clamp(sqrt(逻辑层数 × 铺放面积 / 总件数) / 1.02, 0.3, 0.8)
玩具对照另设 base = 0.45
最终尺寸 = (base + 0～0.036 的变体) × 原类型修正 × 相对尺寸表
```

以水果／农场原半宽 1.35、半深 1.42，4 个逻辑层、300 件计算，基础值仅约 **0.3135**；不同类型的相对倍率即使增加，公共底数仍小。数量越大就越像小粒子，这是本轮直接修正的原因之一。

**【确认·项目代码】** `SeedPoint` 另用 `base×0.85 + 生成层号×0.025` 留边，层号由累计库存推导，并非配置的四个权重层。深处物件越晚生成，铺放越向中央收缩。水果／农场／甜品的逻辑碰撞半宽 1.35～1.42，也明显小于四单位容器外框。

**【确认·项目代码】** R1 相机使用 `max(2.30, 2.15/aspect)`、固定瞄准位置及 320 UI 单位底部留区；容器按四单位制作。它同时留出了横向边距和容器下方间隙，手机比例变化时还会改变这些空隙。

## 3. R2 实际修正

以下全部标为 **【项目适配·截图校准】**，不是声称恢复竞品的精确最终参数。

1. 正式关公共基础尺寸下限设为 **0.70**，保留入门关原来更大的值和 0～0.036 变体。21 类玩具两档均设为 **0.70**。普通 300 件档的基础线性尺寸约为旧版的 2.0～2.2 倍；玩具为旧版的约 1.56 倍，再叠加相机占屏变化。
2. 水果、农场、甜品有效铺放半宽／半深改为 **1.72**；古玩、数码及参考玩具的原范围保留。碰撞仍按每件旋转后的真实代理边界夹取，不靠中心点越过容器口沿。
3. 生成点留边改为 `min(base×0.35, min(halfX,halfZ)×0.18)`，取消随累计层号增加的收缩。随机区间加权、类型配额和逻辑分层继续参与生成，不改完整三件组库存。
4. 相机横向优先显示 **3.90 世界单位**，四单位容器略触画面两侧；底部保留区从 320 改为 **296 UI 单位**，对应七格栏上缘 292 再留 4。相机按容器近沿／相机上向量／当前正交高度计算位置，使底边随屏幕比例贴近栏位。
5. 短屏兜底正交半高 **2.10**，保证完整远沿仍可见；截图比例和长手机不触发该兜底。相机抬到 y=20 仅防止大物堆进入近裁剪面，**正交投影下抬高相机本身不缩小物件**。
6. R1 的单材质、独立凸包／低面容器、局部唤醒、遮挡缓存和 30 Hz 移动档保留。几何面数没有为了放大而增加，原有普通物件单件 4,000 面预算不变。放大可能改变接触、遮挡与可见数，故单独做运行回归。

**【确认·配置守恒】** 正式主题的物品 ID、实际权重数组、15／60／300 件配额和核心参数文件与本轮前一致；参考仍为独立的 126／300 件平衡对照，不改正式进度。

## 5. 验证办法与修正中发现的问题

`GooseScaleAcceptance` 实际加载五主题各 300 件、玩具 126／300 件，待出场和稳定后，投影可见 Renderer 的世界 AABB 八角，记录占屏宽比、可见数、越界及物件中心是否处于世界相机视口。**AABB 会包含旋转后的空角，通常大于真实可见轮廓；不能把该中位数与竞品手工选取的精细轮廓样本直接相等。**

初版在 563×1000、393×852 已通过中心可见检查，但无图形窗口使用了较短的桌面兜底比例，暴露出“只按宽度放大后远沿可能被裁”的问题，通关脚本停在余件阶段。加入短屏半高兜底后重跑；保留初版照片和中断日志，未将它们当作最终通关结果。另修正验收脚本超时暂停时仍等待缩放时间的缺陷，使超时会产生报告，避免把脚本挂起误判成通过。这个等待改动只在开发验收中使用。

## 6. 手机复测入口和仍未确认的内容

R2 微信工程仍在 `unity/Builds/WeChat/minigame`。需对新导出重新预览，首页“对照”弹窗应显示 **比例版本 R2**；正式关与玩具关都已采用新比例。玩具关默认显示 R2 性能行；正式关在暂停里开启“性能数据”。旧 R1 预览码不代表 R2。

**【待确认】** 未连接用户 iPhone，不能宣称新比例在真机上的帧率或触感已经通过；也未恢复截图账号的最终相机热更、模式尺寸、食物模型着色和碰撞网格。模型更大不等于画风完全一致，短屏兜底也不是竞品算法。竞品事实、源码差异、项目修正和运行证据各自保留边界。
