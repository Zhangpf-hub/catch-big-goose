# 微信小游戏《抓大鹅》竞品分析

分析日期：2026-10-21。对象是本机正在运行的微信小游戏《抓大鹅》，AppID `wxb98ac240fd74b0e3`。依据为原生游戏窗口的操作观察、该小游戏自己的本地 Unity 缓存、资源预制体及 IL2CPP 元数据；不以用户的 Cocos 工程作为竞品证据。

**结论：当前烧烤场景采用低面数实物模型、带写实细节的贴图和 Toon／MatCap 材质，配合卡通 UI。玩法在本次观察中表现为有限物品堆的拾取与三件消除，尚未观察到消除后补货。内部配置支持类别、数量、权重和堆积条件控制，不能把它等同于均匀随机生成。**

## 证据范围与可信度

- **直接确认**：真实游戏画面；七个暂存格；连续拾取三根玉米后消除；取走后露出下方原有物件；Unity 资源文件头版本；网格三角数；贴图规格；预制体组件；配置字段及方法名称。
- **结构推断**：关卡配置驱动物品集合，按帧分批生成，分深度／可见性管理物理与显示，对象池用于复用实例。
- **未确认**：实际执行的随机公式、种子、权重数值、三消组构造顺序、是否保证可解、是否随槽位动态调难度、是否有保底、不同尝试是否同布局、每一档关卡的确切总量。方法名称不是方法体，不能据此还原这些规则。
- 本地缓存只覆盖已经下载过的内容；资源包数量和体积不是游戏完整发布包大小。未对加密 wxapkg 解密，未修改游戏数据，也未读取无关聊天内容。

## 一、美术风格

### 1. 物品：低模轮廓，实物贴图承担细节

烧烤玉米、肉串、烤鱼等不是统一的纯色玩具风。轮廓被大幅简化，颜色、烤痕、油光、表面颗粒与局部明暗主要来自贴图。玉米只有 514 个三角形，但 512×512 的颜色贴图直接画出了玉米粒和焦斑，因此画面信息量高于几何复杂度。

卡通白鹅与食物形成明显的造型反差；此次场景中的 `Goose_Pancake` 是大鹅与饼组合的一个预制体，不能把截图中每个饼都当作独立可消物品。

### 2. 材质：Toon 与 MatCap 的混合表现

烧烤物品资源里实际存在名为 `ToonLite1` 的 Shader。材质保存了 `_BaseColor`、`_Matcap`、`_NormalMap`、`_RoughnessMap` 等槽位，以及高光、轮廓光、间接光等控制项。

因此，美术观感不能只通过“纯色材质 + 一盏灯”复现。颜色贴图中的细节和明暗，以及 MatCap 类高光，是重要组成部分。贴图被引用并不代表所有功能均在当前材质中启用，不能仅凭槽位断言它在完整执行标准 PBR。

### 3. 场景与界面

玩法画面近俯视，烧烤网架、炭火、调料和扇子建立具体生活场景。场景也有三维网格资源，不能把整屏内容一概视为背景图。

UI 则采用明亮蓝、黄、绿、奶油白，大圆角、粗描边、立体按钮与白边字。首页活动入口很多，强调限时、奖励与收集；对局界面减少入口，把主要注意力留给物件、七格槽和三个道具。

**对原创同类产品的参考**：优先保证物品在密堆俯视下的轮廓与材质识别，再添加表面细节。不同物件可以同为金黄或棕色，依靠形状、长度、弯曲和贴图纹理区分，不必全部强行做成纯色 Q 版。

## 二、真实资源规格

资源文件头为 **Unity 2021.3.14f1**，缓存组织为 Unity WebGL 数据与 Addressables 风格的 `.bundle`，不是 GLB 模型目录。

本次找到 117 个已缓存的 bundle，合计约 39.24 MiB，另有 WebGL 数据等缓存。烧烤普通物品分布在三个物品包中，三个包合计约 1.45 MiB。它们都是当前缓存样本，不代表完整安装体积或首包大小。

### 贴图

普通食物颜色贴图主要为 128×128、256×256、512×512；小型辅助图还包含 64×64。玉米颜色图为 512×512，法线和 MatCap 为 256×256，AO 与粗糙度图为 128×128。

烧烤普通物品包中的 Texture2D 记录以 ASTC RGB 6×6、8×8 为主，少量为 12×12。共读到 52 条贴图记录；可能包含不同包内的重复依赖，不应当作 52 张唯一贴图。

这些数据支持“较低几何预算 + 小尺寸压缩贴图”的路线。不能将单件贴图都设为 1K、2K，再期待获得同样的资源效率。

### 碰撞、尺寸与状态

预制体中同时存在 `col` 与 `realCol` 引用，以及名为 `Col`、`RealCol`、部分 `FakeCol` 的子物体。碰撞形状以 BoxCollider、CapsuleCollider 为主，部分组合件还有 SphereCollider，多段组合贴合物体。**名称本身不能最终证明哪套用于点击、哪套用于物理，仍需方法体或运行跟踪确认。**

玉米采用胶囊体；串类同时为食物主体和细竹签配置盒体；大鹅组合件的碰撞体明显更复杂。参考其手感时，应把视觉网格和简化交互／物理形状分开设计。

样本物理材质 `ObjMa` 的静摩擦、动摩擦均为 0.6，弹性为 0；这是预制资源值，运行时是否覆盖未验证。

物品还保存 `_pickScale`，例如玉米与肉串样本为 0.6。不同物件有各自的缩放与子节点变换，不存在已经证实的“所有模型最大边统一 1.0”规范。

## 三、核心生成、刷新与三消

### 1. 已实测的循环

对当前关卡连续拾取三根玉米：第一、第二根分别留在暂存槽，第三根进入后整组三根消失；场内其他物品仍存在，下方原有物品露出。期间没有观察到上方投放补货。

因此当前证据支持的循环为：

`初始物品堆 → 选中物品 → 进入七格槽 → 同类三件消除 → 继续清理剩余堆`

不能因为内部有 `RefreshContentDisplay`、对象池的 `Get`、或 `CreateUnitObj`，就判断消除会无限刷新新货：显示刷新、实例复用和新逻辑物品生成是不同事情。

本次仅验证了一组三消，未完整通关、未测试槽满失败、未触发广告或消耗道具。不能把局部结果扩大为所有模式的完整规则。

### 2. 配置决定哪些物品与多少物品

从真实 IL2CPP 类型定义中读到 `LevelDataData` 的字段与对应属性：

| 字段／属性 | 可确认的信息 |
| --- | --- |
| `NameList` | 配置中存在物品名称集合 |
| `SumCount`、`TypeCount` | 总量和种类数分别配置 |
| `CanCreateType` | 有独立的生成类别控制项，确切语义待方法体确认 |
| `WinType`、`WinCount` | 有目标类别与目标计数条件 |
| `WinTypeWeight`、`OtherTypeWeight` | 目标与其他类别有独立权重字段，当前模式是否使用及公式未知 |
| `Height`、`LimitHeight` | 高度与高度限制分别配置 |
| `LimitTime`、`ResumeTime` | 时限与复活补时配置 |
| `SceneObj`、`SceneSize` | 场景资源与尺寸配置 |
| `NetHardName` | 存在网络难度标识字段，不能仅凭字段证明实时动态调难度 |

另有 `LevelABDataData.ReduceGroup / ReduceType`，以及管理器的 `GetMainLevelABOffsetGroupCount / GetMainLevelABOffsetTypeCount`。这些说明代码结构支持按组数和种类数做难度变体，但当前玩家命中了哪档、偏移多少仍未确定。

### 3. 生成并非只有一次洗牌

管理器中确实存在：

- `CreateLevel`、`LoopCreateObj`、`CreateUnitObj`：关卡建立与物件创建接口。
- `_frameMaxCreateCount`、`_maxCreateInterval`、`_createGrowSpeed`：按帧创建量、间隔和出现动画相关参数。
- `LevelObjectPool.Get / Recycle`：物件实例池。
- `_physicFrameCreateCount`、`_physicMaxCreateInterval`、`_physicCreateGrowSpeed`：另有物理创建相关参数。

**合理重建**是先根据关卡配置决定逻辑物品集合，再从预制体池分批建立实例，并安排尺寸、位置、朝向和物理状态。具体调用顺序是结构推断，尚未通过方法体或调用跟踪逐步证实。

### 4. 深度、可见性和物理分开控制

`LevelManager` 包含 `_rigidDepth`、`_maxPhysicObjCount`、`_isUseRealPhysicSpace`、`_layerMinDistance`、`_visibleMinHeight / _visibleMaxHeight`，方法包括 `CheckRigid`、`CheckVisible`、`LoopOptimization`、`GetDynamicVisibleHeight`。

`ObjectUnit` 包含 `SetRigid`、`HideRigid`、`SetVisible`、`CanBeSelect` 与 `IsLockGuidePhysic` 等方法。

这组证据与“深层物品、可见物品、参与物理的物品分别管理”的架构一致。本次取走玉米后其他物品的布局基本保持，不能宣称它每次都让整堆自由塌落，也不能把教学关的表现推到所有关卡。

### 5. 三消、槽位刷新与道具

代码结构中有 `GetUnit`、`GetTriple`、`RefreshContentDisplay`、`DelayToCheckContent`、`DestroyAnim`、`EndCombineObjAnim`、`RefreshTargetCount`、`CheckLevelState`，与实测“拾取—暂存—三件消除—更新目标”的流程相符。具体槽内插入排序及失败判定时点未验证。

道具与物理操作相关方法还包括 `ClawTargetObj`、`GetObjHasThree`、`MessObjPosAnim`、`MessObjRotaAnim`、`ShakeObj`、`WindObj`。它们说明存在查找同类、重排位置和扰动堆的实现接口；本次未使用道具，不能据方法名断言每个道具具体选取策略、是否改数量、是否保证可解。

### 6. 用于原创实现的算法框架

下列是参考竞品结构提出的实现方案，**不是恢复出来的竞品原代码**：

1. 从主题、关卡与难度配置取得候选物品、类型数、数量、目标和时限。
2. 若设计目标是清空所有物品，先按每类三的倍数建立完整逻辑集合；竞品是否采用同一构造法尚未确认。
3. 对逻辑集合做可复现的排列，再按容器形状、层数与轮廓尺寸安排出生点和朝向。随机算法与种子可自行选定，不能声称竞品使用某一种算法。
4. 分帧生成实例，逐步处理显示与物理；限制同时活跃的物理体数量。
5. 拾取只把原有物件转移到暂存槽，凑三后删除；先不引入无证据支持的消除补货。
6. 用种类数、同类离散程度、埋藏深度、可点面积和槽位容量共同控制难度，不能只堆总件数。
7. 将打乱、移出、凑齐分别设计为明确的状态转换，检查操作前后每类总量和可解性。
